### P1: 浏览器技能第 2 阶段 — `/scrape` 和 `/skillify` 技能模板

**内容:** 浏览器技能设计的第 2a 阶段(`docs/designs/BROWSER_SKILLS_V1.md`)。两个新的 gstack 技能:`/scrape <intent>`(只读)是拉取页面数据的单一入口点 — 首次调用通过 `$B` 原语进行原型设计,后续对匹配意图的调用会路由到约 200ms 内完成的成文浏览器技能。`/skillify` 将最近一次成功的原型固化为磁盘上的永久浏览器技能:从代理自身的上下文(仅最终尝试的 $B 调用)合成 `script.ts` + `script.test.ts` + fixture,在临时目录中运行测试,提交前询问,原子重命名到 `~/.gstack/browser-skills/<name>/`。变更流程的兄弟技能 `/automate` 作为独立的 P0 拆分出来(见下文) — 相同的 skillify 模式,不同的信任配置。

**原因:** 第 1 阶段交付了运行时 — 人类可以手写确定性浏览器脚本供 gstack 运行。第 2a 阶段释放了生产力增益:代理通过 20+ 个 `$B` 命令正确完成一次流程后,执行 `/skillify`,脚本就永久变成 200ms 的调用。与 Garry 文章中描述的相同 skillify 模式,应用于最适合确定性压缩的只读浏览器活动(抓取)。变更操作作为 `/automate` 接下来交付,因为失败模式(意外写入)需要更强的门控。

**优点:** 100 倍生产力增益就在这里。闭环:代理原型设计、固化,然后在未来会话中使用固化的技能而不是重新探索。替换了原始的"自创作 `$B` 命令" P1 — 相同的用户可见目标,没有守护进程内隔离问题(技能脚本作为独立的 Bun 进程运行,永远不会导入到守护进程中)。合成问题(Codex 发现 #6)通过从代理自身的对话上下文重新提示来解决(设计文档中的选项 b),根据 `/plan-eng-review` D2 限定为最终尝试的 `$B` 调用。

**缺点:** **Bun 运行时分发**(Codex 发现 #7)。第 1 阶段回避了这个问题,因为捆绑的参考技能随 gstack 安装一起提供。用户创作的技能会落在没有 Bun 的机器上,除非我们随附运行时、编译为自包含二进制文件,或使用 Node + 现有的 `cli.ts` 模式。推迟到第 4 阶段 — `/skillify` 记录了假设 gstack 已安装(这意味着 Bun 在 PATH 中)。

**背景:** 第 1 阶段架构(3 层查找、作用域令牌、兄弟 SDK、frontmatter 契约)已锁定并由捆绑的 `hackernews-frontpage` 参考技能验证。第 2a 阶段通过两个技能模板加一个新辅助函数(`browse/src/browser-skill-write.ts`,用于根据 `/plan-eng-review` D3 的原子临时目录然后重命名)将 `/scrape` 和 `/skillify` 插入该运行时 — 没有新的存储原语。

**工作量:** M(人工:约 1 周 / CC:约 1 天)
**优先级:** P1(此分支 — `garrytan/browserharness` 作为 v1.19.0.0 交付)

### P2: 浏览器技能第 3 阶段 — 会话启动时的解析器注入

**内容:** 在 `browse/src/server.ts:722-743` 镜像域技能解析器。当侧边栏代理会话在具有匹配浏览器技能的主机上启动时,注入一个列表块,告诉代理该主机存在哪些技能以及如何调用它们(`$B skill run <name> --arg ...`)。通过现有的 L1-L6 安全栈进行 UNTRUSTED 包装。添加 `gstack-config browser_skillify_prompts` 开关(默认 `off`),当活动源显示单个主机上有 ≥N 个命令且该主机+意图尚不存在技能时,在 `/qa`、`/design-review` 等任务结束时控制提示。

**原因:** 没有解析器,浏览器技能只有在用户明确输入 `$B skill run <name>` 时才起作用。有了解析器,代理会自动发现当前主机的现有技能并使用它们,而不是重新探索。与域技能相同的复合模式。

**优点:** 填补了可发现性差距。原本不知道技能存在的代理现在会在系统提示中自动看到它。任务结束提示(通过开关选择加入)捕获 skillify 最有价值的时刻。

**缺点:** 解析器块存在于系统提示中,与其他解析器块竞争提示预算。需要仔细控制,使其不会在每个有技能的主机上触发 — 仅当技能与当前任务合理相关时。v1.8.0.0 域技能通过仅对活动标签页的主机名触发来处理此问题;这里采用相同模式。

**工作量:** S(人工:约 3 天 / CC:约 4 小时)
**优先级:** P2
**依赖:** 第 2 阶段。

### P2: 浏览器技能第 4 阶段 — 评估基础设施 + fixture 过时检测 + OS 沙箱

**内容:** 三个松散耦合的扩展:(a) LLM 评判评估("代理是否使用了技能而不是重新探索?"),根据 `test/helpers/touchfiles.ts` 分类为 `periodic`。(b) Fixture 过时检测 — 定期比较捆绑的 fixtures 与实时页面,在它们静默破坏测试之前标记不匹配。(c) 不受信任生成的 OS 级 FS 沙箱:macOS 上的 `sandbox-exec` 配置文件,Linux 上的命名空间/seccomp。在现有的受信任/不受信任契约后面干净地插入(第 1 阶段只是剥离了 env;第 4 阶段添加了真正的 FS 隔离)。

**原因:** 第 1 阶段的信任模型在守护进程端的能力边界上是正确的(作用域令牌),但进程端的 env 清理是卫生措施,而不是沙箱(Codex 发现 #1)。对于真正不受信任的技能(第 2 阶段代理创作),真正的 FS 隔离很重要。评估 + fixture 过时检测在流程漂移时保持技能质量标准诚实。

**优点:** 关闭了 Codex 发现 #1 中最后一个可信的攻击面(FS 读取 `~/.ssh/id_rsa` 等)。评估数据告诉我们解析器注入是否真正起作用。Fixture 过时检测在用户之前捕获 HTML 漂移。

**缺点:** 三个不同的关注点,三个不同的设计过程。很容易捆绑。抵制:每个都可以独立交付。OS 沙箱是最难的部分(macOS `sandbox-exec` 是 Apple 私有但稳定的;Linux 需要命名空间 + 绑定挂载)。

**工作量:** L(人工:约 2-3 周 / CC:约 3-5 天)
**优先级:** P2
**依赖:** 第 2 阶段(需要代理创作的技能来激励沙箱);第 3 阶段(评估需要解析器注入)。

### P2: 将 `/learn` 迁移到 SQLite

**内容:** 当前的 `~/.gstack/projects/<slug>/learnings.jsonl` 存储有效(仅追加、容错解析器、空闲压缩器),但 Codex 外部声音(T5)将 JSONL 标记为"多写入者规范状态的错误原语":重写时丢失更新、崩溃时部分行损坏、无事务。v1.8.0.0 通过 flock + O_APPEND 强化了 JSONL,但正确的长期原语是 SQLite(Bun 通过 `bun:sqlite` 内置)。

**原因:** 域技能现在存在于同一个 `learnings.jsonl` 中(根据 CEO D1 统一)。随着容量增长,JSONL 强化压缩器 + 容错解析器方法成为长杆。SQLite 提供原子事务、索引(对主机名查找非常重要)和崩溃安全性,无需自定义压缩器。

**优点:** 原子写入。真实模式。通过主机名/键/类型进行快速索引查找。崩溃安全。

**缺点:** 迁移涉及 `learnings.jsonl` 的每个消费者 — `/learn` 脚本(`gstack-learnings-log`、`gstack-learnings-search`)、domain-skills.ts 读/写、gbrain-sync(目前将其视为平面文件)。野外的旧 `learnings.jsonl` 文件需要一次性迁移脚本。

**背景:** v1.8.0.0 中的 JSONL 强化对于该发布范围来说是正确的决定(保留统一,不要煮沸海洋)。但失败模式是有界的,而不是消除的。SQLite 是煮沸海洋的修复。

**工作量:** M(人工:约 1 周 / CC:约 1 天)
**优先级:** P2
**依赖:** v1.8.0.0 在生产中约 1 个月以测量 JSONL 痛点(压缩器频率、部分行丢失、写入争用)。

### v1.1+: 审计 `/health` 令牌分发

**内容:** Codex 对 cc-pty-import 的外部声音审查标记了 `/health` 已经在有头模式下向任何 localhost 调用者公开 `AUTH_TOKEN`(`server.ts:1657`)。这是一个预先存在的软泄漏 — 在 localhost 上运行的任何东西都可以通过访问 `/health` 获得根令牌。

**原因:** cc-pty-import 通过不将 PTY 令牌放在那里(改用 HttpOnly cookie 路径)来回避它。但底层泄漏仍然是可交付的表面。第二个扩展或 localhost Web 应用程序目前可以抓取 `AUTH_TOKEN` 并访问任何 browse-server 端点。

**背景:** cc-pty-import 计划工程审查中的 codex 发现 #2。不在该 PR 的范围内;故意推迟以保持 PTY-import 小。

## P2: /plan-ceo-review 的每个发现 AskUserQuestion 计数断言

**内容:** PTY E2E 测试,通过包含 N 个已知发现的稳定 fixture diff 驱动 /plan-ceo-review 通过步骤 0,断言在 plan_ready 之前恰好触发 N 个不同的 AskUserQuestions(每个发现一个)。

**原因:** 技能模板在每个审查检查点重复"一个问题 = 一个 AskUserQuestion 调用。永远不要将多个问题合并为一个问题。"没有测试强制执行它。当前的 `skill-e2e-plan-ceo-plan-mode.test.ts` 冒烟测试(v1.21.1.0 后)只捕获"代理完全跳过步骤 0"。将发现批处理为一个问题会静默通过。

**优点:** 锁定技能强制执行的最强契约。捕获真实的失败模式(原始附件显示 2 个发现批处理为 0 个问题)。

**背景:** PTY 工具(`runPlanSkillObservation`)在第一个终端结果时返回 — 对于 V2,我们需要一个流式变体,在整个会话中计数 AskUserQuestions 直到 `plan_ready`。可能是 `runPlanSkillObservation` 旁边的新辅助函数。

**依赖:** 稳定的 fixture diff(`test/fixtures/plans/multi-finding.diff` 或类似),具有触发所有 4 个审查部分的小型已知问题集。

**优先级:** P2。
**工作量:** S(CC:一旦 fixture 存在约 30 分钟)。从 v1.21.1.0 plan-eng-review D2 捕获。

**缺点:** 涉及所有 3 个平台(linux/darwin/windows)的 gstack-config 二进制文件。跨二进制重构。

## P3: SANCTIONED_WRITE_SUBSTRINGS 上的路径混淆强化

**内容:** `runPlanSkillObservation` 的静默写入检测器对几个批准的路径(`.gstack/`、`CHANGELOG.md`、`TODOS.md` 等)使用子字符串匹配。对 `node_modules/some-pkg/CHANGELOG.md` 或 `src/foo/.gstack/leak.ts` 的写入目前是批准的,因为子字符串在路径中的任何位置匹配。

**原因:** 防御性 — 目前没有错误利用这一点,但恶意技能或 fixture 可能会写入恰好包含 `.gstack/` 或 `CHANGELOG.md` 的路径,并绕过静默写入检测。

**优点:** 强化工具以防止未来技能不当行为。使子字符串规则与其意图一致。
**缺点:** 需要针对绝对前缀(`os.homedir() + '/.gstack/'`、worktree 根)进行锚定,这使得测试在机器之间的可移植性降低。

**背景:** 从 v1.21.1.0 对抗性审查中捕获(HIGH/FIXABLE 发现,预先存在)。在 v1.21.1.0 中重构为 `SANCTIONED_WRITE_SUBSTRINGS` 常量,但子字符串包含逻辑与之前相比没有变化。

**优先级:** P3。
**工作量:** S。

## P1: 所有技能的结构化 STOP-Ask 强制函数

**内容:** 设计并实现一个结构化强制函数,当技能强制执行每个问题 AskUserQuestion 但模型静默替换批量合成时捕获。候选机制:问题计数断言(技能在 frontmatter 中声明预期问题计数;运行后审计日志如果模型触发 <N),类型化问题模板(技能向模型提供预构建的 AskUserQuestion 有效负载而不是散文指令),或基于 canUseTool 的运行后审计,比较声明的门触发与预期。

**原因:** 权威的"计划模式期间的技能调用"规则(提升到前言位置 1)告诉模型 AskUserQuestion 满足计划模式的回合结束要求。这修复了计划模式进入,但不是更广泛的失败类别:每当技能的交互契约与任何其他规则表面(自动模式、工具计数焦虑、认知负荷)冲突时,模型静默替换批量合成为 STOP-Ask 循环。没有结构化执行,每个具有 STOP-per-issue 契约的技能仍然容易受到攻击。

**优点:** 捕获一类错误,而不是一个实例。适用于声明 STOP 门的每个技能。基于 `test/helpers/agent-sdk-runner.ts` 中的 `canUseTool` 原语构建。

**缺点:** 真正的设计工作。技能如何声明预期问题计数 — frontmatter 中的静态
