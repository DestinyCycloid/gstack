# GStack Browser V0 — AI 原生开发浏览器

**日期:** 2026-03-30
**作者:** Garry Tan + Claude Code
**状态:** Phase 1a 已发布,Phase 1b 进行中
**分支:** garrytan/gstack-as-browser

## 核心理念

其他所有 AI 浏览器(Atlas、Dia、Comet、Chrome Auto Browse)都是从消费级浏览器出发,然后在上面添加 AI 功能。GStack Browser 反其道而行之。它以 Claude Code 作为运行时,并为其提供浏览器视口。

Agent 是第一公民。浏览器是画布。技能是一等能力。你不是"使用带 AI 辅助的浏览器",而是使用一个能够看到并与网络交互的 AI。

这是后 IDE 时代的 IDE。代码存在于终端中。产品存在于浏览器中。AI 同时跨两者工作。Cursor 为文本编辑器做的事,GStack Browser 为浏览器做。

## 当前状态(Phase 1a,已发布)

一个可双击的 macOS .app,封装了 Playwright 的 Chromium,并内置了 gstack 侧边栏扩展。打开它,Claude Code 就能看到你的屏幕、导航页面、填写表单、截图、检查 CSS、清理覆盖层,并运行任何 gstack 技能。无需接触终端。

```
GStack Browser.app (389MB, 189MB DMG)
├── 编译的 browse 二进制文件 (58MB) — CLI + HTTP 服务器
├── Chrome 扩展 (172KB) — 侧边栏、活动流、检查器
├── Playwright 的 Chromium (330MB) — 实际的浏览器
└── 启动脚本 — 绑定项目目录,设置环境变量
```

启动 → Chromium 打开并显示侧边栏 → 扩展自动连接到 browse 服务器 → agent 在约 5 秒内就绪。

## 未来规划

### Phase 1b: 开发者体验(下一步)

**命令面板 (Cmd+K):** 标志性交互。打开模糊过滤的技能选择器。输入 "/qa" 开始 QA 测试,"/investigate" 进行调试,"/ship" 创建 PR。技能从 browse 服务器获取,而非硬编码。面板是一切的入口。

**快速截图 (Cmd+Shift+S):** 捕获当前视口并将其传入侧边栏聊天,附带"你看到了什么?"的上下文。AI 分析截图并给出可操作的反馈。一键生成可视化 bug 报告。

**状态栏:** 每个页面底部的持久 30px 栏。显示 agent 状态(空闲/思考中)、工作区名称、当前分支和自动检测的开发服务器。点击开发服务器标签进行导航。始终可见的 AI 工作状态。

**自动检测开发服务器:** 启动时扫描常见端口(3000、3001、4200、5173、5174、8000、8080)。如果只找到一个服务器,自动导航到它。状态栏中的开发服务器标签支持一键切换。

### Phase 2: BoomLooper 集成

侧边栏连接到 BoomLooper 的 Phoenix/Elixir API,而不是本地 `claude -p` 子进程。BoomLooper 提供:

- **多 agent 编排。** 并行生成 5 个 agent,每个都有自己的浏览器标签页。一个运行 QA,一个做设计审查,一个监控回归。
- **Docker 基础设施。** 每个 agent 获得一个隔离的容器。容器内的浏览器测试开发服务器。无端口冲突,无状态泄漏。
- **会话持久化。** Agent 对话在浏览器重启后仍然保留。从上次中断的地方继续。
- **团队可见性。** 你的队友可以实时观察你的 agent 在做什么。就像结对编程,但配对的是 5 个 AI agent,而你是指挥者。

### Phase 3: Browse 作为 BoomLooper 工具

browse 二进制文件成为 BoomLooper 中的 MCP 工具。Docker 容器中的 agent 使用 browse 命令测试开发服务器、截图、填写表单和验证部署。需要跨平台编译(linux-arm64/x64)。

### Phase 4: Chromium 分支(触发门控)

当扩展侧面板遇到硬 API 限制、GStack Browser 向外部用户发布、构建基础设施存在且业务证明维护合理时:分叉 Chromium。采用 Brave 的 `chromium_src` 覆盖模式,CC 驱动的 6 周 rebase(使用 CC 需 2-4 小时 vs 人工 1-2 周)。约修改 20-30 个文件。

### Phase 5: 原生外壳

SwiftUI/AppKit 应用外壳,带原生侧边栏和隔离的 Chromium 服务。完整的平台集成。如果 Chromium 分支包含原生侧边栏,可能被 Phase 4 取代。

## 愿景:AI 浏览器能做什么

### 1. 看到你所看到的

浏览器是 AI 的眼睛。不是通过截图(虽然它也能做到),而是通过 DOM 访问、CSS 检查、网络监控和可访问性树解析。AI 理解页面结构,而不仅仅是像素。

**当前:** `snapshot` 命令返回任何页面的可访问性树表示。AI 可以"看到"每个按钮、链接、表单字段和文本元素。元素引用(`@e1`、`@e2`)让 AI 可以点击、填写和交互。

**下一步:** 实时页面观察。AI 注意到页面何时变化、控制台何时出现错误、网络请求何时失败。无需询问即可主动调试。

**未来:** 视觉理解。AI 比较前后截图以捕获视觉回归。像素级设计审查。"这个按钮向左移动了 3px,字体从 14px 变为 13px。"

### 2. 对所见采取行动

不仅仅是阅读页面,而是像人类用户一样与之交互。

**当前:** 点击、填写、选择、悬停、输入、滚动、上传文件、处理对话框、导航、管理标签页。全部通过 browse 服务器的简单命令实现。

**下一步:** 多步骤用户流程。"登录,进入设置,更改时区,验证确认消息。" AI 链接命令并在每一步进行验证。

**未来:** 自主 QA agent。"测试此页面上的每个链接。填写每个表单。尝试破坏它。" AI 运行详尽的交互测试而无需脚本。发现人类测试人员会遗漏的 bug,因为它尝试人类想不到的组合。

### 3. 边浏览边写代码

这是关键差异化因素。AI 可以在浏览器中看到 bug 并同时在代码中修复它。

**当前:** 侧边栏聊天连接到 Claude Code。你说"这个按钮未对齐",AI 读取 CSS,识别问题并提出修复方案。`/design-review` 技能截图、识别视觉问题,并提交带有前后证据的修复。

**下一步:** 实时重载循环。AI 编辑 CSS/HTML,浏览器自动重载,AI 视觉验证修复。简单的视觉修复无需人工介入。"修复此页面上的所有间距问题"变成 30 秒的任务。

**未来:** 全栈调试。AI 在浏览器中看到 500 错误,读取服务器日志,追踪到失败的行,编写修复,并在浏览器中验证。一个命令:"这个页面坏了。修复它。"

### 4. 理解整个技术栈

浏览器不仅仅是一个视口。它是应用程序健康状况的窗口。

**当前:**
- 控制台日志捕获 — 每个 `console.log`、`console.error` 和警告
- 网络请求监控 — 每个 XHR、fetch、websocket 和静态资源
- 性能指标 — Core Web Vitals、资源时序、绘制事件
- Cookie 和存储检查 — 读写 localStorage、sessionStorage
- CSS 检查 — 计算样式、盒模型、规则级联

**下一步:**
- 网络请求重放 — "用不同参数重放这个失败的请求"
- 性能回归检测 — "这个页面比昨天慢了 200ms"
- 依赖审计 — "这个页面加载了 47 个第三方脚本"
- 可访问性审计 — "这个表单没有标签,这些颜色对比度不足"

**未来:**
- 完整应用遥测 — 实时 CPU、内存、GPU 使用情况
- 跨浏览器测试 — 在 Chrome、Firefox、Safari 上运行相同的测试套件
- 真实用户监控关联 — "这个 bug 影响了 12% 的生产用户"

### 5. 工作区模型

浏览器就是工作区。不是工作区中的一个标签页。而是工作区本身。

**当前:** 每个浏览器会话绑定到一个项目目录。侧边栏显示当前分支。状态栏显示检测到的开发服务器。

**下一步:** 多项目支持。在项目之间切换而不关闭浏览器。每个项目获得自己的标签页集、自己的 agent、自己的上下文。就像 VSCode 工作区,但用于浏览器。

**未来:** 团队工作区。多个开发者共享一个浏览器工作区。看到彼此的 agent 在工作。协作调试,一个人导航,另一个人观察 AI 实时修复问题。

### 6. 技能作为浏览器能力

每个 gstack 技能都成为浏览器能力。

| 技能 | 浏览器能力 |
|-------|-------------------|
| `/qa` | 测试每个页面,发现 bug,修复它们,验证修复 |
| `/design-review` | 截图 → 分析 → 修复 CSS → 再次截图 |
| `/investigate` | 在浏览器中看到错误 → 追踪到代码 → 修复 → 验证 |
| `/benchmark` | 测量页面性能 → 检测回归 → 告警 |
| `/canary` | 监控已部署站点 → 定期截图 → 变化时告警 |
| `/ship` | 运行测试 → 审查差异 → 创建 PR → 在浏览器中验证部署 |
| `/cso` | 在真实浏览器中审计页面的 XSS、开放重定向、点击劫持 |
| `/office-hours` | 浏览竞争对手网站 → 综合观察 → 设计文档 |

命令面板 (Cmd+K) 是中心。你不需要知道技能的存在。你输入你想要的,模糊过滤器找到正确的技能,AI 以浏览器作为上下文运行它。

### 7. 设计循环

AI 驱动的设计是一个循环,而不是交接。

```
生成原型 (GPT Image API)
  → 在浏览器中审查(与实时站点并排)
  → 根据反馈迭代("让标题更高")
  → 批准方向
  → 生成生产 HTML/CSS
  → 在浏览器中预览
  → 使用 /design-review 微调
  → 发布
```

浏览器缩小了"在 Figma 中的样子"和"在生产中的样子"之间的差距。因为 AI 可以同时看到两者。

### 8. 安全循环

在真实浏览器中进行 CSO 审查,而不仅仅是静态分析。

- 向每个输入字段注入 XSS 有效载荷,检查是否执行
- 通过从不同来源重放请求来测试 CSRF
- 通过导航到精心制作的 URL 来检查开放重定向
- 验证 CSP 头实际上被强制执行(而不仅仅是存在)
- 通过实时操作 cookie 和 token 来测试认证流程
- 通过在 iframe 中加载站点来检查点击劫持

静态分析捕获模式。浏览器测试捕获现实。

### 9. 监控循环

部署后的金丝雀监控,在真实浏览器中。

```
部署 → 浏览器加载生产 URL
  → 截图基线
  → 每 5 分钟:截图、比较、检查控制台
  → 告警条件:视觉回归、新的控制台错误、性能下降
  → 如果检测到严重错误则自动回滚
```

具有 AI 判断的合成监控。不仅仅是"页面是否返回 200",而是"页面看起来正确且工作正常"。

## 竞争格局

| 浏览器 | 方法 | 差异化因素 | 弱点 |
|---------|----------|---------------|----------|
| **Atlas** | Chromium 分支 + AI 层 | Agentic 浏览器,"OWL" 隔离 Chromium | 面向消费者,无代码集成 |
| **Dia** | AI 原生浏览器 | 简洁 UI,为 AI 交互而构建 | 无开发工具,无代码编辑 |
| **Comet** | AI 浏览器 | 多 agent 浏览 | 早期,开发工作流不清晰 |
| **Chrome Auto Browse** | 扩展 | Google 自己的,深度 Chrome 集成 | 仅扩展,无代码编辑 |
| **Cursor** | VSCode 分支 + AI | 一流的代码编辑 | 无浏览器视口 |
| **GStack Browser** | CC 运行时 + 浏览器视口 | 在浏览器中看到 bug,在代码中修复,验证 | 目前仅 macOS,无消费者功能 |

GStack Browser 不与消费级浏览器竞争。它与在浏览器和编辑器之间切换的工作流竞争。目标是让这种切换变得不可见。

## 设计系统

来自 DESIGN.md:
- **主要强调色:** Amber-500 (#F59E0B) — agent 活动、焦点状态、脉冲
- **背景:** Zinc-950 (#09090B) 到 Zinc-800 (#27272A) — 深色、密集
- **排版:** JetBrains Mono(代码/状态)、DM Sans(UI/标签)
- **边框半径:** 8px (md)、12px (lg)、full(药丸)
- **动效:** agent 活动时的脉冲动画,200ms 过渡
- **布局:** 侧边栏(右侧)、状态栏(底部)、面板(居中覆盖)

12 个月的理想状态:你打开 GStack Browser,它检测你的项目,启动你的开发服务器,运行你的测试套件,并报告什么坏了。你说"修复它",AI 修复每个 bug,视觉验证每个修复,并创建一个 PR。你在同一个浏览器中审查 PR,批准它,AI 部署它并监控金丝雀。全部在一个窗口中。

这就是浏览器作为 AI 工作区。不是添加了 AI 的浏览器。而是添加了浏览器的 AI。
