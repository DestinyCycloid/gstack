## 问题陈述

GStack 在会话中运行 30 多个技能,但它们之间没有任何学习。一次 /review 会话捕获了 N+1 查询模式,而下一次在同一代码库上的 /review 又从头开始。一次 /ship 运行发现了测试命令,而之后的每次 /ship 都会重新发现它。一次 /investigate 发现了一个棘手的竞态条件,而未来的会话对此一无所知。

每个 AI 编码工具都有这个问题。Cursor 有每用户记忆。Claude Code 有 CLAUDE.md。Windsurf 有持久化上下文。但它们都不会累积。它们都不会结构化所学内容。它们都不会在技能之间共享知识。

## 我们正在构建什么

跨会话和技能累积的每项目机构知识。结构化、类型化、置信度评分的学习内容,每个 gstack 技能都可以读写。目标:在同一代码库上进行 20 次会话后,gstack 知道每个架构决策、每个过去的错误模式,以及每次它出错的情况。

## 北极星

/autoship(第 5 版)。一个命令中的完整工程团队。描述一个功能,批准计划,其他一切都是自动的。/autoship 没有学习内容(R1)、审查质量(R2)、会话持久化(R3)和自适应流程(R4)就无法工作。第 1-4 版是使 /autoship 真正工作的基础设施。

## 受众

使用 AI 构建的 YC 创始人。那些每周在真实代码库上运行 gstack 20 多次,并注意到它何时问了两次相同问题的人。

## 差异化

| 工具 | 记忆模型 | 范围 | 结构 |
|------|-------------|-------|-----------|
| Cursor | 每用户聊天记忆 | 每会话 | 非结构化 |
| CLAUDE.md | 静态文件 | 每项目 | 手动 |
| Windsurf | 持久化上下文 | 每会话 | 非结构化 |
| **GStack** | **每项目 JSONL** | **跨会话、跨技能** | **类型化、评分、衰减** |

## 状态系统

gstack 有四个不同的持久化层。它们共享存储模式(在 `~/.gstack/projects/$SLUG/` 中的 JSONL),但服务于不同的目的:

| 系统 | 文件 | 存储内容 | 写入者 | 读取者 |
|--------|------|---------------|------------|---------|
| **Learnings** | `learnings.jsonl` | 机构知识(陷阱、模式、偏好) | 所有技能 | 所有技能(前言) |
| **Timeline** | `timeline.jsonl` | 事件历史(技能开始/完成、分支、结果) | 前言(自动) | /retro、前言上下文恢复 |
| **Checkpoints** | `checkpoints/*.md` | 工作状态快照(决策、剩余工作、文件) | /checkpoint、/ship、/investigate | 前言上下文恢复、/checkpoint 恢复 |
| **Health** | `health-history.jsonl` | 随时间变化的代码质量分数(每工具、综合) | /health | /retro、/ship(门控)、/health(趋势) |

这些不重叠。Learnings = 你知道什么。Timeline = 发生了什么。Checkpoints = 你在哪里。Health = 代码有多好。每个回答不同的问题。

## 发布路线图

### 第 1 版:"GStack 学习"(v0.13-0.14)— 已发布

**标题:**每次会话都让下一次更智能。

已发布内容:
- 在 `~/.gstack/projects/{slug}/learnings.jsonl` 的学习内容持久化
- `/learn` 技能用于手动审查、搜索、修剪、导出
- 所有审查发现的置信度校准(1-10 分,带显示规则)
- 观察/推断学习内容的置信度衰减(1 分/30 天)
- 跨项目学习内容发现(选择加入,AskUserQuestion 同意)
- 当审查匹配过去的学习内容时显示"已应用学习内容"标注
- 集成到 /review、/ship、/plan-*、/office-hours、/investigate、/retro

模式:
```json
{
  "ts": "2026-03-28T12:00:00Z",
  "skill": "review",
  "type": "pitfall",
  "key": "n-plus-one-activerecord",
  "insight": "Always check includes() for has_many in list endpoints",
  "confidence": 8,
  "source": "observed",
  "branch": "feature-x",
  "commit": "abc1234",
  "files": ["app/models/user.rb"]
}
```

类型:`pattern` | `pitfall` | `preference` | `architecture` | `tool`
来源:`observed` | `user-stated` | `inferred` | `cross-model`

架构:仅追加 JSONL。重复项在读取时解决(每个 key+type 的"最新获胜者")。无写入时变更,无竞态条件。

### 第 2 版:"审查军团"(v0.14.3-0.14.4)— 已发布

**标题:**每个 PR 上有 10 个专业审查员。

已发布内容:
- 7 个并行专业子代理:始终开启(测试、可维护性)+条件性(安全、性能、数据迁移、API 契约、设计)+红队(大型差异/关键发现)
- 带置信度分数的 JSON 结构化发现 + 跨代理的指纹去重
- PR 质量分数(0-10)每次审查记录 + /retro 趋势
- 学习内容驱动的专家提示,每个领域注入过去的陷阱
- 多专家共识突出显示,确认的发现获得提升
- 通过 PLAN_COMPLETION_AUDIT 增强交付完整性
- 检查清单重构:CRITICAL 类别保留在主通道中,专家类别提取到 review/specialists/ 中的专注检查清单

### 第 2.5 版:"审查军团扩展"— 尚未发布

**标题:**在 R2 证明稳定后发布。检查核心循环的表现。

预检查:审查 R2 质量指标(PR 质量分数、专家命中率、误报率、E2E 测试稳定性)。如果核心循环有问题,先修复这些问题。

发布内容:
- E1:自适应专家门控,自动跳过具有 0 发现跟踪记录的专家。通过 gstack-learnings-log 存储每项目命中率。用户可以使用 --security 等强制执行。
- E3:测试桩生成,每个专家在发现旁边输出 TEST_STUB。从项目检测框架(Jest/Vitest/RSpec/pytest/Go test)。流入 Fix-First:AUTO-FIX 应用修复 + 创建测试文件。
- E5:跨审查发现去重,读取 gstack-review-read 以获取先前的审查条目。抑制匹配先前用户跳过的发现的发现。
- E7:专家性能跟踪,通过 gstack-review-log 记录每个专家的指标。Timeline 集成:专家运行出现在 timeline.jsonl 中用于 /retro 趋势。

### 第 3 版:"会话智能"(v0.15.0)— 已发布

**标题:**你的 AI 会话记住发生了什么。

已发布内容:
- 会话时间线:每个技能自动将开始/完成事件记录到 `~/.gstack/projects/$SLUG/timeline.jsonl`。仅本地,从不发送到任何地方,无论遥测设置如何始终开启。
- 上下文恢复:在压缩或会话开始后,前言列出最近的 CEO 计划、检查点和审查。代理读取最近的内容以恢复上下文。
- 跨会话注入:前言为当前分支打印 LAST_SESSION 和 LATEST_CHECKPOINT。在输入任何内容之前,你会看到你离开的地方。
- 预测性技能建议:如果你最近的 3 次会话遵循某种模式(review、ship、review),gstack 会建议你接下来可能想要什么。
- 会话开始时的"欢迎回来"综合上下文消息。
- `/checkpoint` 技能:保存/恢复/列出工作状态快照。跨分支列出用于代理之间的 Conductor 工作区交接。
- `/health` 技能:包装项目工具(tsc、biome、knip、shellcheck、tests)的代码质量记分员。综合 0-10 分数、趋势跟踪、分数下降时的改进建议。
- Timeline 二进制文件:`bin/gstack-timeline-log` 和 `bin/gstack-timeline-read`。
- 路由规则:/checkpoint 和 /health 添加到前言技能路由。

设计文档:`docs/designs/SESSION_INTELLIGENCE.md`

### 第 4 版:"自适应流程"— 尚未发布

**标题:**GStack 尊重你的时间而不损害你的安全。

流程和信任是独立的关注点。流程 = PR 经历的一组审查/测试/QA 步骤。信任 = 确定适用哪个流程级别的策略引擎。它们相互作用但不合并。

发布内容:

**流程级别:**
- FULL:所有专家、对抗性、Codex 结构化审查、覆盖率审计、计划完成。用于大型差异、新功能、迁移、认证更改。
- STANDARD:对抗性 + Codex、覆盖率审计、计划完成。用于中等差异、典型功能工作。
- FAST:仅对抗性。用于受信任项目上的小型、经过良好测试的更改。

**信任策略引擎:**
- 范围感知信任。信任是按更改类别获得的,而不是全局的。仅文档 PR 的干净历史不会为迁移 PR 购买信任。
- 更改类别检测:文档、测试、配置、前端、后端、迁移、认证、基础设施。每个类别都有自己的信任阈值。
- 信任信号:连续干净的审查(按类别)、/health 分数稳定性、回归频率、测试覆盖率趋势。
- 信任从不快速通道:迁移、认证/权限更改、新 API 端点、基础设施更改。无论信任级别如何,这些始终获得 FULL 流程。
- 逐步降级,而非二进制重置。单个回归不会重置所有信任。它会将该更改类别的信任降低一个级别。

**范围评估:**
- 在 /review、/ship、/autoplan 中基于差异大小、触及的文件和更改类别进行 TINY/SMALL/MEDIUM/LARGE 分类。
- 流程级别 = f(范围、信任、更改类别)。

**TODO 生命周期:**
- /triage 用于交互式批准传入的 TODO
- /resolve 用于通过并行代理批量解决

### 第 5 版:"/autoship — 一个命令,完整功能"— 尚未发布

**标题:**描述一个功能。批准计划。其他一切都是自动的。

/autoship 是一个可恢复的状态机,而不是线性管道。审查和 QA 可以将工作发送回构建/修复。压缩可以中断任何阶段。系统必须优雅地恢复。

```
                    ┌──────────┐
                    │  START   │
                    └────┬─────┘
                         │
                    ┌────▼─────┐
                    │ /office- │
                    │  hours   │
                    └────┬─────┘
                         │
                    ┌────▼─────┐
                    │/autoplan │ ◄── 单一批准门
                    └────┬─────┘
                         │
              ┌──────────▼──────────┐
              │       BUILD         │ ◄── /checkpoint 自动保存
              └──────────┬──────────┘
                         │
              ┌──────────▼──────────┐
              │      /health        │ ◄── 质量门
              │   (score >= 7.0)    │
              └──────────┬──────────┘
                         │ fail → 返回 BUILD
              ┌──────────▼──────────┐
              │      /review        │
              └──────────┬──────────┘
                         │ ASK items → 返回 BUILD
              ┌──────────▼──────────┐
              │        /qa          │
              └──────────┬──────────┘
                         │ bugs found → 返回 BUILD
              ┌──────────▼──────────┐
              │       /ship         │
              └──────────┬──────────┘
                         │
              ┌──────────▼──────────┐
              │ /checkpoint archive │ ◄── 保留,不销毁
              └─────────────────────┘
```

发布内容:
- /autoship 自主管道,具有上述状态机。每个阶段写入 timeline.jsonl。检查点在每个阶段之前自动保存。压缩恢复:上下文恢复读取检查点 + 时间线,在最后完成的阶段恢复。
- 完成时的检查点归档(不是删除)。恢复状态被保留用于调试失败的 autoship 运行。
- /ideate 头脑风暴技能(并行发散代理 + 对抗性过滤)
- /plan-eng-review 中的研究代理(代码库分析师、历史分析师、最佳实践研究员、学习内容研究员)

依赖于:R1(研究代理的学习内容)、R2(质量的审查军团)、R3(持久化的会话智能)、R4(速度的自适应流程)。

## 风险登记册

### 代理信号作为跳过审查的许可
(由 Codex 审查识别,2026-04-01)

/health 分数、干净的审查历史和时间线模式是有用的信号。它们不是安全的证明。如果这些信号提供流程减少和 /autoship,失败模式是罕见的、无声的、高严重性的错误。缓解措施:
- 某些更改类别从不快速通道(迁移、认证、基础设施、新端点)。
- 信任逐步降级,而非二进制重置。
- /autoship 在每个项目的第一次运行时始终运行 FULL 流程。信任是赢得的。

### 陈旧的上下文恢复
(由 Codex 审查识别,2026-04-01)

上下文恢复可能注入错误分支状态、过时的计划或无效的检查点。缓解措施:
- 检查点在 YAML 前言中包含分支名称。上下文恢复按当前分支过滤。
- Timeline grep 在显示 LAST_SESSION 之前按分支过滤。
- 陈旧工件检测:如果检查点超过 7 天,将其标记为可能陈旧,而不是作为当前呈现。

### 需要验证指标
(由 Codex 审查识别,2026-04-01)

在发布 R4(自适应流程)之前,测量:
- 预测性建议准确性(用户是否运行了建议的技能?)
- 信任策略误跳过率(快速通道的 PR 是否有合并后问题?)
- 上下文恢复准确性(恢复的上下文是否与实际状态匹配?)
- /health 分数与实际代码质量的相关性(高分是否预测更少的生产错误?)

这些指标应在 R3 使用期间收集,并在 R4 发布前审查。

## 致谢灵感

自学习路线图的灵感来自 Nico Bailon 的 [Compound Engineering](https://github.com/nicobailon/compound-engineering) 项目的想法。他们对学习内容持久化、并行审查代理和自主管道的探索催化了 GStack 方法的设计。我们调整了每个概念以适应 GStack 的模板系统、语气和架构,而不是直接移植。
