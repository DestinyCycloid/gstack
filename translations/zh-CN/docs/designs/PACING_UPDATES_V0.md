**提取自:** [PLAN_TUNING_V1.md](./PLAN_TUNING_V1.md),在实现过程中,当审查严格性揭示了 pacing 工作流存在无法通过计划文本编辑修复的结构性缺陷时提取。

**审查计划:** CEO + Codex + DX + Eng 循环,与 V1 相同的严格性。

这个计划的存在要归功于 **[Louise de Sadeleer](https://x.com/LouiseDSadeleer/status/2045139351227478199)**。她在架构审查期间的"yes yes yes"不仅仅是关于术语(V1 解决了这个问题)——而是关于节奏和主动性。在过长的审查过程中有太多打断性的决策。V1.1 解决了节奏这一半的问题。

## 问题

Louise 在阅读 gstack 审查输出时的疲劳来自两个方面:

1. **术语密度** — 技术术语出现时没有解释。*已在 V1 中解决(ELI10 写作风格)。*
2. **打断数量** — `/autoplan` 运行 4 个阶段(CEO + Design + Eng + DX),每个阶段有 5-10 个 AskUserQuestion 提示。总计约 30-50 个提示,持续约 45 分钟。非技术用户在约 10-15 次打断后就会失去注意力。**这就是 V1.1。**

仅仅翻译并不能解决打断数量的问题。翻译后的打断仍然是打断。修复需要改变发现何时浮现,而不仅仅是如何措辞。

## 为什么要提取(来自 V1 第三次工程审查 + Codex 第二轮的结构性缺陷)

在 V1 规划期间,起草了一个 pacing 工作流:对发现进行排序,自动接受双向门,每个审查阶段最多 3 个 AskUserQuestion 提示,为自动接受的项目设置 Silent Decisions 块,"flip <id>" 命令用于事后重新打开自动接受的决策。第三次工程审查 + 第二次 Codex 审查发现了 10 个无法通过计划文本编辑解决的缺陷:

1. **会话状态模型未定义。** Pacing 需要每个阶段的状态(哪些发现已浮现,哪些已自动接受,用户可以翻转哪些)。V1 有用于术语解释的每次技能调用状态,但没有用于每个阶段 pacing 记忆的后备存储。
2. **问题日志中缺少阶段标识符。** Silent Eng #8 希望在一个阶段内超过 3 个提示时发出警告。V0 的 `question-log.jsonl` 没有 `phase` 字段。V1 声称"无模式更改"——与执行目标矛盾。
3. **问题注册表 ≠ 发现注册表。** V0 的 `scripts/question-registry.ts` 涵盖*问题*(在技能定义时注册)。审查发现是*动态的*(在运行时发现)。通过注册表执行 `door_type: one-way` 不涵盖临时发现。对于代理在审查中生成的发现,单向门安全性无法强制执行。
4. **作为散文的 Pacing 无法反转现有控制流。** V1 计划在前言散文中添加"对发现进行排序,然后询问"规则。但现有的技能模板如 `plan-eng-review/SKILL.md.tmpl` 具有每个部分的 STOP/AskUserQuestion 序列。前言中的散文规则无法可靠地覆盖硬编码的每个部分 STOP。行为变化是排序,而不是提示措辞。
5. **翻转机制没有实现。** "回复 `flip <id>` 以更改"只是散文。没有命令解析器,没有状态存储,没有重放行为。如果对话压缩且 Silent Decisions 块离开上下文,原始决策就会丢失。
6. **迁移提示本身就是一个打断。** V1 的升级后迁移提示(提供恢复 V0 散文)计入 V1.1 试图减少的打断预算。V1.1 必须决定:从预算中豁免,还是作为第 1-N 次打断包含在内?
7. **首次运行前言提示也计数。** Lake 介绍、遥测、主动、路由注入——Louise 在首次运行时看到了所有这些。它们是在第一个真正的技能运行之前的打断。V1.1 必须审核其中哪些对新用户是必需的,哪些可以推迟到第 N 次会话。
8. **排序公式未根据真实数据校准。** V1 考虑了 `product 0-8`(损坏:`{0,1,2,4,8}` 分布),然后是 `sum 0-6`,阈值 ≥ 4。但两者都没有根据实际发现分布进行验证。V1.1 应该对 V0 问题日志进行检测,以测量真实发现的样子,然后进行校准。
9. **"每个单向门都浮现"与"每个阶段最多 3 个"矛盾。** 单向上限 = 无上限(安全);双向上限 = 3。但计划同时有两个规则,没有明确的优先级。V1.1 必须声明:无论阶段预算如何,单向门都无上限地浮现。
10. **未定义的验证值。** V1 计划有"Silent Decisions 块 ≥ N 个条目",N 从未定义,吞吐量 JSON 中的 `active: true` 字段也从未定义。V1.1 获得具体值。

## V1.1 的范围

1. **定义会话状态模型。** 每次技能调用 vs 每个阶段 vs 每次对话。后备存储:可能是 `~/.gstack/sessions/<session_id>/pacing-state.json` 的 JSON 文件,记录每个阶段哪些发现已浮现 vs 自动接受。清理:与前言中现有会话跟踪相同的 TTL。

2. **向 question-log.jsonl 模式添加 `phase` 字段。** 按审查阶段(CEO / Design / Eng / DX / other)对每个 AskUserQuestion 进行分类。迁移:现有条目默认为 `"unknown"`。非破坏性模式扩展。

3. **扩展动态发现的注册表覆盖范围。** 两个选项,在 CEO 审查期间选择:
   - (a) 扩展 `scripts/question-registry.ts` 以允许运行时注册(临时 ID 仍会被记录 + 分类)。
   - (b) 添加辅助运行时分类器 `scripts/finding-classifier.ts`,使用模式匹配将发现文本映射到风险层级。

4. **将 pacing 从前言散文移至技能模板控制流。** 更新每个审查技能模板以:(i) 内部完成阶段,(ii) 使用 `gstack-pacing-rank` 二进制文件对发现进行排序,(iii) 发出最多 3 个 AskUserQuestion 提示,(iv) 为其余部分发出 Silent Decisions 块。不是前言规则——每个模板中的显式序列。

5. **翻转机制实现。** 新二进制文件 `bin/gstack-flip-decision`。命令解析器接受用户消息中的 `flip <id>`。在 pacing-state.json 中查找原始决策。重新打开为显式 AskUserQuestion。新选择持久化。

6. **迁移提示预算决策。** 明确规则:一次性迁移提示从每个阶段的打断预算中豁免。理由:它们在审查阶段开始之前触发,而不是在期间。

7. **首次运行前言审核。** 审核 lake 介绍、遥测、主动、路由注入。对于每个:这对首次用户是必需的,还是可以推迟?可能的结果:除了 lake 介绍外,其他都抑制到第 2 次会话以后。通过 `/plan-tune first-run` 命令提供其余的,用户可以自愿调用。

8. **排序阈值校准。** 对 V0 的问题日志进行检测(已经运行,有历史记录)。测量最近 CEO + Eng + DX + Design 审查中 `severity × irreversibility × user-decision-matters` 的实际分布。根据真实数据选择阈值。目标:约 20% 的发现浮现,约 80% 自动接受。

9. **明确规则:单向门无上限。** 在技能模板散文中硬编码:"无论阶段打断预算如何,单向门都会浮现。" 双向发现每个阶段上限为 3 个。

10. **具体验证值。** 为 Silent Decisions 定义 `N`(例如,对于非平凡计划,预期 ≥ 5 个条目),使用具体字段名称定义吞吐量 JSON 模式。

## V1.1 的验收标准

- **打断次数:** Louise(或类似的非技术协作者)在与 V0 基线相当的计划上端到端重新运行 `/autoplan`。AskUserQuestion 次数 ≤ V0 基线的 50%。(V1 为 V1.1 校准捕获此基线记录。)
- **单向门覆盖率:** 100% 的安全关键决策(`door_type: one-way` 或分类器标记的动态发现)以完整的技术细节单独浮现。无上限。
- **翻转往返:** 用户输入 `flip test-coverage-bookclub-form`。原始自动接受的决策重新打开为 AskUserQuestion。用户的新选择持久化到 Silent Decisions 块(或者如果用户翻转为显式浮现则被删除)。
- **每个阶段的可观察性:** `/plan-tune` 可以显示任何会话的每个阶段 AskUserQuestion 次数,从 question-log.jsonl 的新 `phase` 字段读取。
- **首次运行减少:** 新用户在第一个真正的技能运行之前看到 ≤ 1 个元提示(lake 介绍),而 V1 是 4 个(lake + 遥测 + 主动 + 路由)。
- **人工重新运行:** Louise + Garry 独立定性审查,与 V1 相同的模式。

## 审查计划

- **前期工作:** 从当前 V0 数据中捕获真实的问题日志分布。用作范围 #8 的校准输入。
- **CEO 审查。** 前提挑战:pacing 是正确的修复方案,还是 V1.1 应该考虑完全删除阶段?(例如,将 CEO + Design + Eng + DX 合并为单个统一审查过程。)范围模式:可能是选择性扩展(pacing 是核心,相关改进是精选)。
- **Codex 审查。** 对 V1.1 计划进行独立审查。预计对控制流更改(范围 #4)进行特别审查,因为这是 V1 遇到困难的领域。

- **工程审查 ×N。** 预计多次审查,与 V1 相同。
