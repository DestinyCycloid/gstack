## `/office-hours`

这是每个项目应该开始的地方。

在你计划之前,在你评审之前,在你写代码之前——与 YC 风格的合作伙伴坐下来思考你实际在构建什么。不是你认为你在构建什么。是你*实际*在构建什么。

### 重新定义框架

这是一个真实项目中发生的事情。用户说:"我想为我的日历构建一个每日简报应用。"合理的请求。然后它询问痛点——具体例子,而不是假设。他们描述了助手遗漏事项、跨多个 Google 账户的日历项目信息过时、准备文档是 AI 垃圾、事件位置错误需要很长时间才能追踪。

它回复说:*"我要挑战这个框架,因为我认为你已经超越了它。你说'多 Google 日历管理的每日简报应用'。但你实际描述的是个人首席幕僚 AI。"*

然后它提取了用户没有意识到自己在描述的五个能力:

1. **监视你的日历**——跨所有账户检测过时信息、缺失位置、权限缺口
2. **生成真正的准备工作**——不是物流摘要,而是为董事会会议、播客、筹款活动做准备的*智力工作*
3. **管理你的 CRM**——你要见谁、关系是什么、他们想要什么、历史是什么
4. **优先安排你的时间**——标记何时需要提前开始准备、主动阻止时间、按重要性排列事件
5. **用金钱换杠杆**——主动寻找委派或自动化的方法

这个重新定义改变了整个项目。他们本来要构建一个日历应用。现在他们正在构建价值十倍的东西——因为这个技能倾听了他们的痛点而不是他们的功能请求。

### 前提挑战

重新定义框架后,它提出前提供你验证。不是"这听起来好吗?"——而是关于产品的实际可证伪声明:

1. 日历是锚定数据源,但价值在于其上的智能层
2. 助手不会被替换——他们会被增强
3. 最窄的楔子是一个真正有效的每日简报
4. CRM 集成是必须的,而不是锦上添花

你同意、不同意或调整。你接受的每个前提都成为设计文档中的承重部分。

### 实现替代方案

然后它生成 2-3 个具体的实现方法,并提供诚实的工作量估计:

- **方法 A:首先每日简报**——最窄的楔子,明天发布,M 工作量(人类:约 3 周 / CC:约 2 天)
- **方法 B:CRM 优先**——首先构建关系图,L 工作量(人类:约 6 周 / CC:约 4 天)
- **方法 C:完整愿景**——一次性完成所有,XL 工作量(人类:约 3 个月 / CC:约 1.5 周)

推荐 A,因为你从实际使用中学习。CRM 数据在第二周自然出现。

### 两种模式

**创业模式**——面向创始人和内部创业者构建业务。你会得到从 YC 合作伙伴如何评估产品中提炼出的六个强制性问题:需求现实、现状、绝望的具体性、最窄的楔子、观察与惊喜以及未来适应性。这些问题故意让人不舒服。如果你不能说出需要你产品的具体人,那是在写任何代码之前最重要的学习内容。

**构建者模式**——面向黑客马拉松、副项目、开源、学习和娱乐。你会得到一个热情的合作者,帮助你找到你想法的最酷版本。什么会让人说"哇"?分享某些东西的最快路径是什么?问题是生成性的,而不是审问性的。

### 设计文档

两种模式都以写入 `~/.gstack/projects/` 的设计文档结束——该文档直接输入到 `/plan-ceo-review` 和 `/plan-eng-review`。完整的生命周期现在是:`office-hours → plan → implement → review → QA → ship → retro`。

设计文档批准后,`/office-hours` 反思它在会话期间注意到的你的思考方式——不是泛泛的赞美,而是对你所说内容的具体回调。观察也出现在设计文档中,所以你以后重新阅读时会再次遇到它们。

## `/plan-ceo-review`

这是我的**创始人模式**。

这是我希望模型以品味、雄心、用户同理心和长远眼光思考的地方。我不希望它字面理解请求。我希望它首先问一个更重要的问题:

**这个产品实际上是为了什么?**

我把这看作**Brian Chesky 模式**。

重点不是实现明显的工单。重点是从用户的角度重新思考问题,找到感觉不可避免、令人愉悦、甚至有点神奇的版本。

### 示例

假设我正在构建一个 Craigslist 风格的列表应用,我说:

> "让卖家为他们的物品上传照片。"

一个弱的助手会添加一个文件选择器并保存图像。

那不是真正的产品。

在 `/plan-ceo-review` 中,我希望模型询问"照片上传"是否甚至是功能。也许真正的功能是帮助某人创建一个真正能卖出去的列表。

如果那是真正的工作,整个计划就会改变。

现在模型应该问:

* 我们能从照片中识别产品吗?
* 我们能推断 SKU 或型号吗?
* 我们能搜索网络并自动起草标题和描述吗?
* 我们能提取规格、类别和定价比较吗?
* 我们能建议哪张照片作为主图转化率最高吗?
* 我们能检测上传的照片是否丑陋、黑暗、杂乱或低信任度吗?
* 我们能让体验感觉高端而不是像 2007 年的死表单吗?

这就是 `/plan-ceo-review` 为我做的。

它不只是问,"我如何添加这个功能?"
它问,**"隐藏在这个请求中的 10 星产品是什么?"**

### 四种模式

- **范围扩展**——大胆梦想。代理提出雄心勃勃的版本。每个扩展都作为你选择加入的单独决策呈现。热情推荐。
- **选择性扩展**——将你当前的范围作为基线,但看看还有什么可能。代理逐一呈现机会,提供中立建议——你挑选值得做的。
- **保持范围**——对现有计划的最大严格性。不呈现扩展。
- **范围缩减**——找到最小可行版本。削减其他一切。

愿景和决策持久化到 `~/.gstack/projects/`,因此它们在对话之外存活。卓越的愿景可以提升到你仓库中的 `docs/designs/` 供团队使用。

## `/plan-eng-review`

这是我的**工程经理模式**。

一旦产品方向正确,我想要完全不同的智能。我不想要更多蔓延的构思。我不想要更多"如果...会不会很酷"。我希望模型成为我最好的技术负责人。

这种模式应该确定:

* 架构
* 系统边界
* 数据流
* 状态转换
* 故障模式
* 边界情况
* 信任边界
* 测试覆盖率

对我来说一个令人惊讶的大解锁:**图表**。

当你强制 LLM 绘制系统时,它们会变得更加完整。序列图、状态图、组件图、数据流图,甚至测试矩阵。图表强制将隐藏的假设公开化。它们使含糊的计划变得更加困难。

所以 `/plan-eng-review` 是我希望模型构建能够承载产品愿景的技术骨架的地方。

### 示例

采用相同的列表应用示例。

假设 `/plan-ceo-review` 已经完成了它的工作。我们决定真正的功能不只是照片上传。它是一个智能列表流程:

* 上传照片
* 识别产品
* 从网络丰富列表
* 起草强有力的标题和描述
* 建议最佳主图

现在 `/plan-eng-review` 接管。

现在我希望模型回答这样的问题:

* 上传、分类、丰富和草稿生成的架构是什么?
* 哪些步骤同步发生,哪些进入后台作业?
* 应用服务器、对象存储、视觉模型、搜索/丰富 API 和列表数据库之间的边界在哪里?
* 如果上传成功但丰富失败会发生什么?
* 如果产品识别置信度低会发生什么?
* 重试如何工作?
* 我们如何防止重复作业?
* 什么时候持久化什么,什么可以安全地重新计算?

这就是我想要图表的地方——架构图、状态模型、数据流图、测试矩阵。图表强制将隐藏的假设公开化。它们使含糊的计划变得更加困难。

这就是 `/plan-eng-review`。

不是"让想法变小。"
**让想法可构建。**

### 评审就绪仪表板

每次评审(CEO、工程、设计)都会记录其结果。在每次评审结束时,你会看到一个仪表板:

```
+====================================================================+
|                    评审就绪仪表板                                    |
+====================================================================+
| 评审          | 运行次数 | 最后运行            | 状态      | 必需 |
|-----------------|------|---------------------|-----------|----------|
| 工程评审      |  1   | 2026-03-16 15:00    | 通过      | 是       |
| CEO 评审      |  1   | 2026-03-16 14:30    | 通过      | 否       |
| 设计评审      |  0   | —                   | —         | 否       |
+--------------------------------------------------------------------+
| 结论:已通过 — 工程评审通过                                           |
+====================================================================+
```

工程评审是唯一必需的门(使用 `gstack-config set skip_eng_review true` 禁用)。CEO 和设计是信息性的——分别推荐用于产品和 UI 更改。

### 计划到 QA 流程

当 `/plan-eng-review` 完成测试评审部分时,它会将测试计划工件写入 `~/.gstack/projects/`。当你稍后运行 `/qa` 时,它会自动获取该测试计划——你的工程评审直接输入到 QA 测试中,无需手动复制粘贴。

## `/plan-design-review`

这是我的**高级设计师评审你的计划**——在你写一行代码之前。

大多数计划描述后端做什么,但从不指定用户实际看到什么。空状态?错误状态?加载状态?移动布局?AI 垃圾风险?这些决策被推迟到"在实现期间解决"——然后工程师发布"未找到项目。"作为空状态,因为没有人指定更好的东西。

`/plan-design-review` 在计划期间捕获所有这些,当修复成本低时。

它的工作方式类似于 `/plan-ceo-review` 和 `/plan-eng-review`——交互式,一次一个问题,使用 **STOP + AskUserQuestion** 模式。它对每个设计维度评分 0-10,解释 10 分是什么样子,然后编辑计划以达到目标。评分驱动工作:评分低 = 大量修复,评分高 = 快速通过。

对计划进行七次审查:信息架构、交互状态覆盖、用户旅程、AI 垃圾风险、设计系统对齐、响应式/可访问性和未解决的设计决策。对于每次审查,它找到缺口并直接修复它们(明显的)或要求你做出设计选择(真正的权衡)。

### 示例

```
你:   /plan-design-review

Claude: 初始设计评分:4/10

        "这个计划描述了一个用户仪表板,但从未指定
         用户首先看到什么。它说'带图标的卡片'——
         看起来像每个 SaaS 模板。它提到零
         加载状态、零空状态,没有移动行为。"

        第 1 次审查(信息架构):3/10
        "10 分会为每个屏幕定义主要/次要/第三级内容
         层次结构。"
        → 向计划添加了信息层次结构部分

        第 2 次审查(交互状态):2/10
        "计划有 4 个 UI 功能,但指定了 20 个交互状态中的 0 个
         (4 个功能 × 每个 5 个状态)。"
        → 向计划添加了交互状态表

        第 4 次审查(AI 垃圾):4/10
        "计划说'带卡片和图标的干净、现代 UI'
         和'带渐变的英雄部分'。这些是前 2 个
         AI 生成外观的模式。"
        → 用具体、有意的替代方案重写了 UI 描述

        总体:4/10 → 修复后 8/10
        "计划设计完整。实现后运行 /design-review
         进行视觉 QA。"
```

当你重新运行它时,已经达到 8+ 的部分会快速通过。低于 8 的部分会得到完整处理。对于实现后的实时站点视觉审计,使用 `/design-review`。

## `/design-consultation`

这是我的**设计合作伙伴模式**。

`/plan-design-review` 审计已经存在的站点。`/design-consultation` 用于当你还没有任何东西时——没有设计系统、没有字体选择、没有调色板。你从零开始,你想要一个高级设计师与你坐下来一起构建整个视觉识别。

这是一次对话,而不是一个表单。代理询问你的产品、你的用户和你的受众。它思考你的产品需要传达什么——信任、速度、工艺、温暖,无论什么合适——并从中倒推到具体选择。然后它提出一个完整、连贯的设计系统:美学方向、排版(3+ 种具有特定角色的字体)、带十六进制值的调色板、间距比例、布局方法和动作策略。每个建议都有理由。每个选择都强化其他选择。

但连贯性是基本要求。每个开发工具仪表板看起来都一样——干净的无衬线字体、柔和的灰色、蓝色强调色。它们都是连贯的。它们都是可忘记的。一个看起来"不错"的产品和一个人们真正认识的产品之间的区别是**刻意的创意风险**:标题的意外衬线、你类别中没有其他人使用的大胆强调色、使你的数据感觉权威而不是空灵的更紧密间距。

这就是 `/design-consultation` 真正的意义。它不只是提出一个安全的系统。它提出安全的选择和风险——并告诉你哪个是哪个。"这些是让你在你的类别中保持识字的选择。这是我认为你应该打破惯例的地方,以及为什么。"你选择承担哪些风险。代理检查整个系统是否仍然连贯。

如果你愿意,代理会研究你的领域中已经存在的东西——截取真实站点的屏幕截图,分析它们的字体、颜色
