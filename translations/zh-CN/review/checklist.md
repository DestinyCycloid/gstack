# 上线前审查清单

## 说明

审查 `git diff origin/main` 输出中列出的问题。要具体——引用 `文件:行号` 并建议修复方案。跳过没问题的内容。只标记真正的问题。

**两轮审查:**
- **第一轮(关键):** 首先运行 SQL 与数据安全、竞态条件、LLM 输出信任边界、Shell 注入和枚举完整性检查。最高严重性。
- **第二轮(信息性):** 运行下面剩余的类别。严重性较低但仍需处理。
- **专项类别(由并行子代理处理,不在此清单中):** 测试缺口、死代码、魔法数字、条件副作用、性能与打包影响、加密与熵。参见 `review/specialists/` 了解这些内容。

所有发现通过修复优先审查处理:明显的机械性修复自动应用,
真正模糊的问题批量整合为单个用户问题。

**输出格式:**

```
上线前审查: N 个问题(X 个关键,Y 个信息性)

**已自动修复:**
- [文件:行号] 问题 → 已应用修复

**需要输入:**
- [文件:行号] 问题描述
  建议修复: 建议的修复方案
```

如果未发现问题: `上线前审查: 未发现问题。`

保持简洁。每个问题:一行描述问题,一行说明修复方案。无需开场白、总结或"整体看起来不错"。

## 审查类别

### 第一轮 — 关键

#### SQL 与数据安全
- SQL 中的字符串插值(即使值是 `.to_i`/`.to_f` — 使用参数化查询(Rails: sanitize_sql_array/Arel; Node: 预处理语句; Python: 参数化查询))
- TOCTOU 竞态:检查后设置的模式应该是原子性的 `WHERE` + `update_all`
- 绕过模型验证的直接数据库写入(Rails: update_column; Django: QuerySet.update(); Prisma: 原始查询)
- N+1 查询:在循环/视图中使用的关联缺少预加载(Rails: .includes(); SQLAlchemy: joinedload(); Prisma: include)

#### 竞态条件与并发
- 读取-检查-写入操作没有唯一性约束或捕获重复键错误并重试(例如,`where(hash:).first` 然后 `save!` 但不处理并发插入)
- find-or-create 没有唯一数据库索引 — 并发调用可能创建重复项
- 状态转换未使用原子性的 `WHERE old_status = ? UPDATE SET new_status` — 并发更新可能跳过或重复应用转换
- 对用户控制的数据进行不安全的 HTML 渲染(Rails: .html_safe/raw(); React: dangerouslySetInnerHTML; Vue: v-html; Django: |safe/mark_safe)(XSS)

#### LLM 输出信任边界
- LLM 生成的值(邮箱、URL、姓名)在写入数据库或传递给邮件发送器之前未进行格式验证。在持久化前添加轻量级防护(`EMAIL_REGEXP`、`URI.parse`、`.strip`)。
- 结构化工具输出(数组、哈希)在数据库写入前未进行类型/结构检查就被接受。
- LLM 生成的 URL 在获取时未使用白名单 — 如果 URL 指向内部网络存在 SSRF 风险(Python: `urllib.parse.urlparse` → 在 `requests.get`/`httpx.get` 前检查主机名是否在黑名单中)
- LLM 输出存储在知识库或向量数据库中未经清理 — 存在存储型提示注入风险

#### Shell 注入(Python 特定)
- `subprocess.run()` / `subprocess.call()` / `subprocess.Popen()` 使用 `shell=True` 且在命令字符串中使用 f-string/`.format()` 插值 — 改用参数数组
- `os.system()` 使用变量插值 — 替换为使用参数数组的 `subprocess.run()`
- 对 LLM 生成的代码使用 `eval()` / `exec()` 且未进行沙箱隔离

#### 枚举与值完整性
当 diff 引入新的枚举值、状态字符串、层级名称或类型常量时:
- **追踪所有使用方。** 阅读(不只是 grep — 要阅读)每个对该值进行 switch、过滤或显示的文件。如果任何使用方未处理新值,标记它。常见遗漏:在前端下拉菜单中添加值但后端模型/计算方法未持久化它。
- **检查白名单/过滤数组。** 搜索包含同级值的数组或 `%w[]` 列表(例如,如果向层级添加 "revise",找到每个 `%w[quick lfg mega]` 并验证需要的地方是否包含 "revise")。
- **检查 `case`/`if-elsif` 链。** 如果现有代码对枚举进行分支,新值是否会落入错误的默认分支?
执行方法:使用 Grep 查找所有对同级值的引用(例如,grep "lfg" 或 "mega" 以找到所有层级使用方)。阅读每个匹配项。此步骤需要阅读 diff 之外的代码。

### 第二轮 — 信息性

#### 异步/同步混用(Python 特定)
- 在 `async def` 端点内使用同步的 `subprocess.run()`、`open()`、`requests.get()` — 阻塞事件循环。改用 `asyncio.to_thread()`、`aiofiles` 或 `httpx.AsyncClient`。
- 在异步函数内使用 `time.sleep()` — 使用 `asyncio.sleep()`
- 在异步上下文中进行同步数据库调用且未使用 `run_in_executor()` 包装

#### 列/字段名称安全
- 验证 ORM 查询中的列名(`.select()`、`.eq()`、`.gte()`、`.order()`)是否与实际数据库模式匹配 — 错误的列名会静默返回空结果或抛出被吞没的错误
- 检查查询结果上的 `.get()` 调用是否使用实际选择的列名
- 在可用时与模式文档交叉引用

#### 死代码与一致性(仅版本/变更日志 — 其他项由可维护性专家处理)
- PR 标题与 VERSION/CHANGELOG 文件之间的版本不匹配
- CHANGELOG 条目不准确地描述更改(例如,"从 X 改为 Y" 但 X 从未存在)

#### LLM 提示问题
- 提示中的 0 索引列表(LLM 可靠地返回 1 索引)
- 提示文本列出的可用工具/能力与 `tool_classes`/`tools` 数组中实际连接的不匹配
- 在多个地方声明的词/令牌限制可能会漂移

#### 完整性缺口
- 快捷实现,而完整版本只需 <30 分钟 CC 时间(例如,部分枚举处理、不完整的错误路径、缺少直接添加的边缘情况)
- 仅提供人工团队工作量估算的选项 — 应同时显示人工和 CC+gstack 时间
- 测试覆盖缺口,其中添加缺失的测试是"湖泊"而非"海洋"(例如,缺少负向路径测试、缺少镜像正向路径结构的边缘情况测试)
- 功能实现达到 80-90% 而 100% 可通过适度的额外代码实现

#### 时间窗口安全
- 假设"今天"覆盖 24 小时的日期键查找 — 太平洋时间上午 8 点的报告在今天的键下只能看到午夜→上午 8 点
- 相关功能之间时间窗口不匹配 — 一个使用小时桶,另一个对相同数据使用日键

#### 边界处的类型强制转换
- 跨越 Ruby→JSON→JS 边界的值,类型可能改变(数字 vs 字符串) — 哈希/摘要输入必须规范化类型
- 哈希/摘要输入在序列化前未调用 `.to_s` 或等效方法 — `{ cores: 8 }` vs `{ cores: "8" }` 产生不同的哈希

#### 视图/前端
- 局部视图中的内联 `<style>` 块(每次渲染都重新解析)
- 视图中的 O(n*m) 查找(循环中的 `Array#find` 而非 `index_by` 哈希)
- Ruby 端对数据库结果进行 `.select{}` 过滤,而这本可以是 `WHERE` 子句(除非有意避免前导通配符 `LIKE`)

#### 分发与 CI/CD 流水线
- CI/CD 工作流更改(`.github/workflows/`):验证构建工具版本是否匹配项目要求,工件名称/路径是否正确,密钥使用 `${{ secrets.X }}` 而非硬编码值
- 新工件类型(CLI 二进制文件、库、包):验证是否存在发布/发行工作流并针对正确的平台
- 跨平台构建:验证 CI 矩阵是否覆盖所有目标 OS/架构组合,或记录哪些未测试
- 版本标签格式一致性:`v1.2.3` vs `1.2.3` — 必须在 VERSION 文件、git 标签和发布脚本之间匹配
- 发布步骤幂等性:重新运行发布工作流不应失败(例如,`gh release create` 前先 `gh release delete`)

**不要标记:**
- 具有现有自动部署流水线的 Web 服务(Docker 构建 + K8s 部署)
- 不在团队外分发的内部工具
- 仅测试的 CI 更改(添加测试步骤,而非发布步骤)

## 修复优先启发式

此启发式由 `/review` 和 `/ship` 引用。它决定代理是自动修复发现还是询问用户。

```
自动修复(代理不询问直接修复):         询问(需要人工判断):
├─ 死代码 / 未使用的变量                ├─ 安全(认证、XSS、注入)
├─ N+1 查询(缺少预加载)                 ├─ 竞态条件
├─ 与代码矛盾的过时注释                ├─ 设计决策
├─ 魔法数字 → 命名常量                  ├─ 大型修复(>20 行)
├─ 缺少 LLM 输出验证                    ├─ 枚举完整性
├─ 版本/路径不匹配                      ├─ 移除功能
├─ 已赋值但从未读取的变量              └─ 任何改变用户可见行为的内容
└─ 内联样式、O(n*m) 视图查找
```

**经验法则:** 如果修复是机械性的且资深工程师会不经讨论就应用,则为自动修复。如果合理的工程师可能对修复方案有不同意见,则为询问。

**关键发现默认倾向于询问**(它们本质上风险更高)。
**信息性发现默认倾向于自动修复**(它们更机械化)。

## 抑制 — 不要标记这些

- "X 与 Y 冗余" 当冗余无害且有助于可读性时(例如,`present?` 与 `length > 20` 冗余)
- "添加注释解释为何选择此阈值/常量" — 阈值在调优期间会改变,注释会腐化
- "此断言可以更严格" 当断言已经覆盖行为时
- 建议仅为一致性的更改(将值包装在条件中以匹配另一个常量的保护方式)
- "正则表达式不处理边缘情况 X" 当输入受约束且 X 在实践中从不发生时
- "测试同时检验多个防护" — 这没问题,测试不需要隔离每个防护
- 评估阈值更改(max_actionable、最小分数) — 这些是根据经验调优的且经常变化
- 无害的空操作(例如,对从不在数组中的元素进行 `.reject`)
- 你正在审查的 diff 中已经解决的任何内容 — 在评论前阅读完整的 diff
