# 每周工程回顾

生成全面的工程回顾,分析提交历史、工作模式和代码质量指标。支持团队协作:识别运行命令的用户,然后分析每个贡献者,包含每个人的表扬和成长机会。

## 参数

- 默认:最近 7 天
- `24h`:最近 24 小时
- `14d`:最近 14 天
- `30d`:最近 30 天
- `compare`:对比当前时间窗口与前一个相同长度的时间窗口

## 说明

解析参数以确定时间窗口。默认为 7 天。所有时间应以用户的**本地时区**报告。

**午夜对齐的时间窗口:** 对于天单位,计算本地午夜的绝对起始日期。例如,如果今天是 2026-03-18,时间窗口是 7 天,则起始日期是 2026-03-11。对 git log 查询使用 `--since="2026-03-11T00:00:00"`。对于小时单位,使用 `--since="N hours ago"`。

---

### 步骤 1:收集原始数据

首先,拉取 origin 并识别当前用户:

```bash
git fetch origin main --quiet
git config user.name
git config user.email
```

`git config user.name` 返回的名称是**"你"**...阅读此回顾的人。所有其他作者都是团队成员。

运行所有这些 git 命令(它们是独立的):

```bash
# 所有提交及其时间戳、主题、哈希、作者、更改的文件
git log origin/main --since="<window>" --format="%H|%aN|%ae|%ai|%s" --shortstat

# 每次提交的测试与总代码行数分解及作者
git log origin/main --since="<window>" --format="COMMIT:%H|%aN" --numstat

# 用于会话检测和每小时分布的提交时间戳
git log origin/main --since="<window>" --format="%at|%aN|%ai|%s" | sort -n

# 最频繁更改的文件(热点分析)
git log origin/main --since="<window>" --format="" --name-only | grep -v '^$' | sort | uniq -c | sort -rn

# 从提交消息中提取 PR 编号
git log origin/main --since="<window>" --format="%s" | grep -oE '[#!][0-9]+' | sort -t'#' -k1 | uniq

# 每个作者的文件热点
git log origin/main --since="<window>" --format="AUTHOR:%aN" --name-only

# 每个作者的提交计数
git shortlog origin/main --since="<window>" -sn --no-merges

# 测试文件计数
find . -name '*.test.*' -o -name '*.spec.*' -o -name '*_test.*' -o -name '*_spec.*' 2>/dev/null | grep -v node_modules | wc -l

# 时间窗口内更改的测试文件
git log origin/main --since="<window>" --format="" --name-only | grep -E '\.(test|spec)\.' | sort -u | wc -l
```

---

### 步骤 2:计算指标

在摘要中计算并呈现这些指标:

- **提交到 main:** N
- **贡献者:** N
- **合并的 PR:** N
- **总插入行数:** N
- **总删除行数:** N
- **净增加代码行数:** N
- **测试代码行数(插入):** N
- **测试代码比例:** N%
- **版本范围:** vX.Y.Z → vX.Y.Z
- **活跃天数:** N
- **检测到的会话数:** N
- **平均每会话小时代码行数:** N

然后在下方立即显示**每个作者的排行榜**:

```
贡献者             提交数   +/-          主要领域
你 (garry)              32   +2400/-300   browse/
alice                    12   +800/-150    app/services/
bob                       3   +120/-40     tests/
```

按提交数降序排序。当前用户始终显示在第一位,标记为"你 (名称)"。

---

### 步骤 3:提交时间分布

显示本地时间的每小时直方图:

```
小时  提交数  ████████████████
 00:    4      ████
 07:    5      █████
 ...
```

识别:
- 高峰时段
- 空白时段
- 双峰模式(早晨/晚上)与连续模式
- 深夜编码集群(晚上 10 点后)

---

### 步骤 4:工作会话检测

使用连续提交之间的**45 分钟间隔**阈值检测会话。

会话分类:
- **深度会话**(50+ 分钟)
- **中等会话**(20-50 分钟)
- **微型会话**(<20 分钟,单次提交)

计算:
- 总活跃编码时间
- 平均会话长度
- 每小时活跃时间的代码行数

---

### 步骤 5:提交类型分解

按约定式提交前缀分类(feat/fix/refactor/test/chore/docs)。显示为百分比条:

```
feat:     20  (40%)  ████████████████████
fix:      27  (54%)  ███████████████████████████
refactor:  2  ( 4%)  ██
```

如果修复比例超过 50%,则标记...表明"快速发布,快速修复"模式,可能表明审查存在差距。

---

### 步骤 6:热点分析

显示前 10 个最常更改的文件。标记:
- 更改 5 次以上的文件(变动热点)
- 热点列表中的测试文件与生产文件
- VERSION/CHANGELOG 频率

---

### 步骤 7:PR 大小分布

估算 PR 大小并分桶:
- **小型**(<100 行代码)
- **中型**(100-500 行代码)
- **大型**(500-1500 行代码)
- **超大型**(1500+ 行代码)

---

### 步骤 8:专注度分数 + 本周之星

**专注度分数:** 涉及单个最常更改的顶级目录的提交百分比。越高 = 更深入的专注工作。越低 = 分散的上下文切换。

**本周之星:** 时间窗口内单个代码行数最多的 PR。突出显示 PR 编号、更改的代码行数以及其重要性。

---

### 步骤 9:团队成员分析

对于每个贡献者(包括当前用户),计算:

1. **提交和代码行数**...总提交数、插入行数、删除行数、净代码行数
2. **关注领域**...他们最常涉及的目录/文件(前 3 个)
3. **提交类型组合**...他们个人的 feat/fix/refactor/test 分解
4. **会话模式**...他们何时编码(高峰时段)、会话计数
5. **测试纪律**...他们个人的测试代码行数比例
6. **最大成果**...他们单个影响最大的提交或 PR

**对于当前用户("你"):** 最深入的处理。包括所有会话分析、时间模式、专注度分数。以第一人称框架呈现。

**对于每个团队成员:** 2-3 句话涵盖他们发布的内容和模式。然后:

- **表扬**(1-2 个具体事项):基于实际提交。不是"做得好"...而是准确说明好在哪里。
- **成长机会**(1 个具体事项):框架为升级,而非批评。基于实际数据。

**如果是单人仓库:** 跳过团队分解。

**AI 协作:** 如果提交有 `Co-Authored-By` AI 尾注,将"AI 辅助提交"作为单独的指标跟踪。

---

### 步骤 10:周环比趋势(如果时间窗口 >= 14 天)

分成每周桶并显示趋势:
- 每周提交数(总计和每个作者)
- 每周代码行数
- 每周测试比例
- 每周修复比例
- 每周会话计数

---

### 步骤 11:连续记录跟踪

从今天往回计算至少有 1 次提交的连续天数:

```bash
# 团队连续记录
git log origin/main --format="%ad" --date=format:"%Y-%m-%d" | sort -u

# 个人连续记录
git log origin/main --author="<user_name>" --format="%ad" --date=format:"%Y-%m-%d" | sort -u
```

显示两者:
- "团队发布连续记录:47 天"
- "你的发布连续记录:32 天"

---

### 步骤 12:加载历史并对比

检查 `memory/` 中的先前回顾历史:

如果存在先前的回顾,加载最近的一个并计算增量:

```
                    上次        现在         增量
测试比例:            22%    →    41%         ↑19pp
会话数:              10     →    14          ↑4
每小时代码行数:      200    →    350         ↑75%
修复比例:            54%    →    30%         ↓24pp (改善中)
```

如果不存在先前的回顾,注明"首次记录回顾,下周再次运行以查看趋势。"

---

### 步骤 13:保存回顾历史

将 JSON 快照保存到 `memory/retro-YYYY-MM-DD.json`,包含指标、作者、版本范围、连续记录和可发推文的摘要。

---

### 步骤 14:撰写叙述

**Telegram 格式**(项目符号、粗体,最终输出中不使用 markdown 表格)。

结构:

**可发推文的摘要**(第一行):
> 3 月 1 日周:47 次提交(3 个贡献者),3.2k 行代码,38% 测试,12 个 PR,高峰:晚上 10 点 | 连续记录:47 天

然后是各部分:

- **摘要**...关键指标
- **与上次回顾的趋势**...增量(如果是首次回顾则跳过)
- **时间和会话模式**...团队何时编码、会话长度、深度与微型
- **发布速度**...提交类型、PR 大小、修复链检测
- **代码质量信号**...测试比例、热点、变动
- **专注度和亮点**...专注度分数、本周之星
- **你的一周**...当前用户的个人深度分析
- **团队分解**...每个团队成员的分析,包含表扬 + 成长(如果是单人则跳过)
- **团队前 3 大成就**...发布的最高影响力事项
- **3 个需要改进的方面**...具体、可操作、基于提交
- **下周的 3 个习惯**...小型、实用、现实(<5 分钟采用)

---

## 对比模式

当用户说"compare"时:
- 为当前时间窗口运行回顾
- 为前一个相同长度的时间窗口运行回顾
- 并排呈现指标,用箭头显示改善/退步
- 关于最大变化的简要叙述

---

## 重要规则

- **所有时间均为本地时区。** 永远不要设置 `TZ`。
- **Telegram 格式。** 使用项目符号和粗体。最终输出中避免使用 markdown 表格。
- **表扬基于提交。** 永远不要在不指明好在哪里的情况下说"做得好"。
- **成长领域基于数据。** 永远不要在没有证据的情况下批评。
- **保存历史。** 每次回顾都保存到 `memory/` 以进行趋势跟踪。
- **完成状态:**
  - DONE...回顾已生成,历史已保存
  - DONE_WITH_CONCERNS...已生成但缺少数据(例如,没有用于对比的先前回顾)
  - BLOCKED...不在 git 仓库中或时间窗口内没有提交
