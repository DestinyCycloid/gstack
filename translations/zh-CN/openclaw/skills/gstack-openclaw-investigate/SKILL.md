# 系统化调试

## 铁律

**没有根本原因调查就不要修复。**

修复症状会导致打地鼠式调试。每个没有解决根本原因的修复都会让下一个 bug 更难找到。先找到根本原因,然后再修复它。

---

## 阶段 1:根本原因调查

在形成任何假设之前先收集上下文。

1. **收集症状:** 阅读错误消息、堆栈跟踪和复现步骤。如果用户没有提供足够的上下文,一次问一个问题。不要一次问五个问题。

2. **阅读代码:** 从症状追溯代码路径到潜在原因。搜索所有引用,阅读失败点周围的逻辑。

3. **检查最近的更改:**
   ```bash
   git log --oneline -20 -- <affected-files>
   ```
   之前是正常工作的吗?发生了什么变化?回归意味着根本原因在差异中。

4. **复现:** 你能确定性地触发这个 bug 吗?如果不能,在继续之前收集更多证据。

5. **检查记忆**中关于同一区域的先前调试会话。同一文件中反复出现的 bug 是架构问题的征兆。

输出:**"根本原因假设:..."** ... 一个关于什么出错以及为什么出错的具体、可测试的声明。

---

## 阶段 2:模式分析

检查这个 bug 是否匹配已知模式:

**竞态条件** ... 间歇性的,依赖时序的。查看对共享状态的并发访问。

**Nil/null 传播** ... NoMethodError、TypeError。可选值上缺少保护。

**状态损坏** ... 数据不一致,部分更新。检查事务、回调、钩子。

**集成失败** ... 超时,意外响应。外部 API 调用,服务边界。

**配置漂移** ... 本地工作,在 staging/prod 失败。环境变量、功能标志、数据库状态。

**过期缓存** ... 显示旧数据,清除缓存后修复。Redis、CDN、浏览器缓存。

还要检查:
- 项目中的已知问题是否有相关问题
- Git 日志中同一区域的先前修复。同一文件中反复出现的 bug 是架构问题的征兆,不是巧合。

**外部搜索:** 如果 bug 不匹配已知模式,在线搜索错误类型。**先清理:** 删除主机名、IP、文件路径、SQL、客户数据。搜索错误类别,而不是原始消息。

---

## 阶段 3:假设测试

在编写任何修复之前,验证你的假设。

1. **确认假设:** 在疑似根本原因处添加临时日志语句、断言或调试输出。运行复现。证据是否匹配?

2. **如果假设错误:** 搜索错误(先清理敏感数据)。返回阶段 1。收集更多证据。不要猜测。

3. **三振出局规则:** 如果 3 个假设都失败,**停止**。告诉用户:

   "已测试 3 个假设,都不匹配。这可能是架构问题而不是简单的 bug。"

   选项:
   - 用新假设继续调查(描述它)
   - 上报人工审查(需要了解系统的人)
   - 添加日志并等待(对该区域进行检测并在下次捕获它)

**危险信号** ... 如果你看到以下任何情况,放慢速度:
- "暂时快速修复" ... 没有"暂时"。要么正确修复,要么上报。
- 在追踪数据流之前提出修复 ... 你在猜测。
- 每次修复都会在其他地方暴露新问题 ... 错误的层次,不是错误的代码。

---

## 阶段 4:实现

一旦根本原因得到确认:

1. **修复根本原因,而不是症状。** 消除实际问题的最小更改。

2. **最小差异:** 触及最少的文件,更改最少的行。抵制重构相邻代码的冲动。

3. **编写回归测试**:
   - 没有修复时**失败**(证明测试是有意义的)
   - 有修复时**通过**(证明修复有效)

4. **运行完整的测试套件。** 不允许回归。

5. **如果修复触及 >5 个文件:** 在继续之前向用户标记影响范围。对于 bug 修复来说这很大。

---

## 阶段 5:验证和报告

**全新验证:** 复现原始 bug 场景并确认它已修复。这不是可选的。

运行测试套件。

输出结构化调试报告:

**调试报告**
- **症状:** 用户观察到的现象
- **根本原因:** 实际出错的地方
- **修复:** 更改了什么,包含文件引用
- **证据:** 测试输出,显示修复有效的复现
- **回归测试:** 新测试的位置
- **相关:** 同一区域的先前 bug,架构说明
- **状态:** DONE | DONE_WITH_CONCERNS | BLOCKED

将报告保存到 `memory/` 并标注今天的日期,以便未来的会话可以引用它。

---

## 重要规则

- **3+ 次失败的修复尝试:停止并质疑架构。** 错误的架构,不是失败的假设。
- **永远不要应用你无法验证的修复。** 如果你无法复现和确认,就不要发布它。
- **永远不要说"这应该能修复它"。** 验证并证明它。运行测试。
- **如果修复触及 >5 个文件:** 在继续之前向用户标记。
- **完成状态:**
  - DONE ... 找到根本原因,应用修复,编写回归测试,所有测试通过
  - DONE_WITH_CONCERNS ... 已修复但无法完全验证(例如,间歇性 bug,需要 staging 环境)
  - BLOCKED ... 调查后根本原因不清楚,已上报
